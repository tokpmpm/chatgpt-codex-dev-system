# AI WORKFLOW

## Goal

Deliver work in one controlled path instead of using the user as an iterative QA loop or manual prompt relay.

## State machine

```text
PLANNING
  → CODEX_READY
  → CODEX_RUNNING
  → CI_PENDING
  → REVIEWING
      → REVIEW_APPROVED
      → REPAIR_AWAITING_PLAN
      → REVIEW_ERROR

REPAIR_AWAITING_PLAN
  → REPAIR_APPROVED
  → CODEX_RUNNING
  → CI_PENDING
  → REVIEWING (DELTA REVIEW)

After 2 failed formal repair rounds
  → CODEX_NEEDS_HUMAN
```

GitHub labels mirror the operational state where practical; GitHub itself remains the live source for PR/CI/review status.

## Standard delivery

1. ChatGPT converts the request into a scoped Issue with measurable Acceptance Criteria.
2. Classify risk: LOW, MEDIUM, or HIGH.
3. Once the Issue is approved, the Runner reads the durable repo/GitHub inputs and automatically generates the Developer prompt.
4. The Runner invokes Codex non-interactively; the user does not copy/paste the prompt.
5. For MEDIUM/HIGH, Codex follows the One-Shot Delivery protocol before editing.
6. Run targeted tests, required real-flow validation, negative/failure cases, and full regression.
7. Commit and push a feature branch.
8. Run CI against the exact pushed SHA.
9. Only after that exact SHA passes CI may the Runner generate the Reviewer prompt from the exact SHA/diff/evidence and launch a fresh isolated Reviewer.
10. Reviewer returns `APPROVE`, `REQUEST_CHANGES`, or `REVIEW_ERROR`.
11. `APPROVE` enters the release gate; merge/deploy still require explicit user approval.

## Automatic prompt rule

Developer, Reviewer, and approved Repair execution prompts are generated by the Runner from approved durable inputs. Manual prompt copy/paste is not part of the normal workflow.

Prompt generation must be reproducible and auditable: every model execution records a run ID, input Issue/PR, relevant SHAs, prompt hash, model/provider, and result state in GitHub evidence.

## Risk classification

- **LOW** — isolated documentation/copy/style change with no persistence, auth, money, destructive operation, shared state, or critical flow.
- **MEDIUM** — user-visible behavior, state transitions, API/data flow, responsive UI, or meaningful regression surface.
- **HIGH** — auth/permissions, money, destructive writes, migrations, production infrastructure, concurrency/shared state, security-sensitive data, or broad architectural change.

When uncertain, choose the higher class.

## Reviewer error path

`REVIEW_ERROR` means the reviewer execution failed, not the product.

- Keep the same product SHA.
- Do not increment repair round.
- Do not call Developer/Codex.
- Do not rerun regression or CI merely because reviewer infrastructure failed.
- The Runner may auto-generate a fresh Reviewer prompt and retry a fresh isolated reviewer once.
- If the retry also fails, mark `review-error` and require human/infrastructure handling.

## Review-only recovery

Recovery is explicit opt-in for the case where product SHA is unchanged and exact-SHA CI already passed. The Runner may generate and execute only a fresh Independent Reviewer prompt. It must not modify or revalidate the product through Developer/Codex.

## Repair path

A reviewer blocker is analyzed by ChatGPT first. Codex must not invent a repair plan. The user approves the plan before execution. After approval, the Runner automatically generates the repair prompt from the approved Repair Plan and invokes Codex. Formal product repairs are capped at two rounds; a further attempt must be separately recorded as a user-approved exceptional repair, never as a silent increase to the configured limit.
