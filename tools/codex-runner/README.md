# Local Codex Runner (`ai-dev`)

## Status

Executable v1 implemented on the Runner feature branch. Normal operation requires **zero manual Developer/Reviewer prompt relay**: the Runner reads durable GitHub/repository state, generates prompts, invokes model adapters, validates, pushes, gates on exact-SHA CI, and launches review.

The Runner is infrastructure, not a product decision-maker. Merge and production deploy remain protected human decisions.

## Prerequisites

- Git
- Python 3
- GitHub CLI (`gh`) authenticated to the target repository
- Codex CLI authenticated locally
- this framework present in the product repository
- a product-specific `ci/ai-verify.sh` that performs real validation

Current Codex CLI treats `--ask-for-approval` as a global flag, so the supported launcher uses:

```text
codex --ask-for-approval never exec ...
```

Developer uses `workspace-write`; Reviewer and Repair Planner use `read-only` by default. Adapter commands and models can be overridden by config or environment variables.

## Install

```bash
bash tools/codex-runner/install.sh
```

Default locations:

```text
~/.local/share/ai-dev/releases/<version>
~/.local/share/ai-dev/current
~/.local/bin/ai-dev
```

The installer is transactional: it stages a copy, runs deterministic tests, activates via atomic symlink replacement, runs the installed-copy self-test, and restores the previous active version if activation validation fails.

## Commands

```text
ai-dev status
ai-dev start --issue <n>
ai-dev review --sha <sha> [--issue <n>]
ai-dev approve-repair --plan <plan-id> [--issue <n>]
ai-dev repair --plan <plan-id> [--issue <n>]
ai-dev recover-review --sha <sha> [--issue <n>]
ai-dev self-test
```

`start --issue` performs the guarded normal flow:

```text
Issue/AC/repo state
→ branch + dirty-tree guards
→ generated Developer prompt
→ non-interactive Codex
→ repository validation
→ commit + push
→ exact-SHA CI PASS
→ generated FULL Reviewer prompt
→ fresh isolated review
```

## Automatic prompt inputs

Developer Prompt uses:

- `AGENTS.md`
- `docs/PROJECT_STATE.md`
- workflow/review/repair protocols
- current GitHub Issue body + Acceptance Criteria
- current input SHA
- approved Repair Plan when repairing

Reviewer Prompt uses:

- FULL vs DELTA review mode
- current Issue + Acceptance Criteria
- exact pushed product SHA
- exact diff from merge base
- exact-SHA CI evidence
- previous blocker evidence + approved Repair Plan for DELTA review

Prompts are generated by code and hashed in the audit ledger. Users do not copy/paste them during normal execution.

## Audit evidence

Every model execution records at least:

- `RUN_ID`
- role
- Issue
- exact input SHA
- SHA-256 of generated prompt
- provider/model
- start/end timestamps
- result status/summary
- repair round when applicable

A local copy is stored under Git metadata (`.git/ai-dev/runs/`). The supported `entrypoint.py` also requires a durable GitHub audit confirmation and fails closed if that evidence cannot be written.

## Reviewer isolation

Reviewer execution is guarded by:

1. clean product worktree
2. requested SHA equals current product `HEAD`
3. exact-SHA CI is already `PASS`
4. fresh detached worktree at that SHA
5. read-only Reviewer adapter by default
6. post-run dirty-worktree check before accepting reviewer output

Valid outcomes are:

- `APPROVE`
- `REQUEST_CHANGES`
- `REVIEW_ERROR`

A provider timeout/error or malformed reviewer output is `REVIEW_ERROR`, not a product failure.

## Repair flow

```text
REQUEST_CHANGES
→ fresh Repair Planner produces minimal plan
→ GitHub records PLAN_ID / TARGET_SHA / REPAIR_ROUND
→ explicit approval record
→ ai-dev repair --plan <id>
→ generated Repair Prompt
→ Codex repair
→ validation + new SHA + exact-SHA CI
→ DELTA Review
```

Codex cannot invent an unapproved Repair Plan. Normal formal repair maximum is 2. A further attempt requires a separately recorded exceptional approval; the normal limit is never changed to 3.

## Review-only recovery

`ai-dev recover-review --sha <sha>` requires:

- same product SHA
- prior `REVIEW_ERROR` for that SHA
- existing exact-SHA CI PASS
- clean worktree

Recovery may invoke only fresh Reviewer sessions. It performs no Developer call, product edit, regression rerun, CI rerun, commit, push, merge, or deploy. A provider execution error during recovery gets at most one fresh retry on the same SHA.

## Configuration

Copy `config.example.json` to `ai-dev.config.json` in the product repo and adjust provider/model commands if needed. Environment overrides are also supported:

```text
AI_DEV_CONFIG
AI_DEV_DEVELOPER_CMD
AI_DEV_REVIEWER_CMD
AI_DEV_PLANNER_CMD
AI_DEV_DEVELOPER_MODEL
AI_DEV_REVIEWER_MODEL
AI_DEV_PLANNER_MODEL
```

Using different models/providers for Developer and Reviewer is recommended when available; the workflow requires a fresh isolated reviewer session even if the same provider is used.

## Deterministic verification

```bash
bash tools/codex-runner/self-test.sh
```

The fixture suite covers:

- successful zero-manual-prompt flow
- `REQUEST_CHANGES` → approved Repair → DELTA Review
- Reviewer provider error + retry
- repeated Reviewer error
- exact-SHA CI guard
- Repair approval guard
- review-only recovery
- formal repair round cap
- dirty-worktree guard before Reviewer/Planner
- recovery retry on unchanged SHA

The same suite runs against source, staged, and installed copies. Real model calls are not made by these fixtures.
